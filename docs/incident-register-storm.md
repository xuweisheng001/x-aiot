# 事故复盘：/register 风暴（历史项目）与本项目的回灌

> 这是一次真实发生在既往项目上的线上事故的复盘。写进本仓库的目的不是追责，
> 而是把每一条教训对应到本项目的一个具体设计决策，防止同一件事以另一种形态再发生一次。

## 1. 事故时间线

| 阶段 | 现象 |
|---|---|
| T0 | 一批设备的 JWT 在同一时间窗集中过期（同一批固件、同一天激活、同样的 token 有效期） |
| T0+ | 设备 token 失效后统一走 `/register` 重新注册：该路径 **没有缓存、没有索引、没有限流** |
| T0+1min | 设备固件的失败重试是 **固定 5s**，不退避、不抖动；失败越多，请求越密 |
| T0+3min | MySQL 连接池被 `/register` 的全表扫描占满，其它业务 SQL 排队；CPU 打满 |
| T0+5min | 生产线激活接口（同一个库）不可用，**生产线停线 30 分钟** |
| T0+30min | 手工扩容 + 临时封 IP 段后恢复 |

## 2. 六轮修复

| 轮次 | 动作 | 结果 | 教训 |
|---|---|---|---|
| 1 | 给 `/register` 加 Redis 缓存 | 命中率极低——每台设备只注册一次，缓存本质无效 | 先看请求分布再决定加什么 |
| 2 | 按 IP 限流 | 误伤：**局域网 NAT 后面几百台设备共用一个出口 IP**，正常设备被一起拒 | 限流维度要和「谁在发请求」对齐 |
| 3 | 改按 userId 限流 | 误伤：**一个用户绑多台设备**，多设备同时重连就被限 | 同上，维度错了就是新事故 |
| 4 | 对慢 SQL `EXPLAIN` | 发现 `WHERE digest = ?` 在无索引列上 **全表扫描** | 这才是根因；前三轮都在治症 |
| 5 | 给 digest 加唯一索引 | 单次查询从数百 ms 降到 <1ms；同等 QPS 下库压力消失 | **索引才是真正的修复** |
| 6 | 限流维度改为 `deviceId + path`，放在 Security 中间件之后 | 既不误伤 NAT 用户，也不误伤多设备用户 | 限流是最后一道保险，不是修复本身 |

另一个几乎被忘掉的动作：事故期间为了止血 **临时关掉了一段签名校验**。三天后才有人想起来打开。
教训：**任何「临时关闭」的保护措施，必须在关闭那一刻同时创建一个到点报警的回滚提醒**，否则就是永久关闭。

## 3. 每条教训如何回灌到本项目

| 教训 | 本项目的对应实现 | 位置 |
|---|---|---|
| 固定 5s 重试是风暴放大器 | 退避 `min(2^n·base, 15min) + rand(0,30s)` 被定义为**固件红线**，第一版固件必须固化；`device-simulator -bad-firmware` 专门模拟不退避的坏固件用于演练 | `internal/pkg/backoff`（含上限与抖动单测）、spec §3/§6 |
| IP / userId 都是错的限流维度 | `/api/v1/oem/verify` 的限流 key = `deviceId + path`，且放在 `Security` 中间件之后（先拿到身份再限流）；rps 1 burst 2，同设备第 3 次即 429 | `internal/cf001/handler.go` `Security` / `DeviceLimiter`，`handler_test.go` |
| IP 限流并非完全没用——在**尚无身份**的入口它是唯一可用维度 | `/api/v1/oem/sign` 是设备还没有 SN 的时候调用的，按 IP 10 次/分钟，接受 NAT 误伤风险并写进文档 | `internal/cf001/handler.go` `IPLimiter` |
| 全表扫描是根因 | `cf001.digest_maps.digest` 是 **主键**（天然唯一索引），`sn` 唯一；幂等查询与并发竞态都靠它 | `sql/cf001.sql`，`service.go` `existing()` |
| 库被打死时其它业务陪葬 | conn-gate 上游熔断：dial 连续失败 N 次 → 30s 内对新连接直接 RST，不再往已经塌陷的上游送流量 | conn-gate（spec §6） |
| 令牌集中过期 = 同步风暴 | 认证接口按 `gate:{cell}:handshake` 令牌桶限握手速率，把尖峰压成平台 | conn-gate、bootstrap `retry_after` |
| 临时关闭的保护必须带回滚报警 | OTA 熔断 `fused` **没有自动恢复**，只有人工 `POST /resume`；alarm-svc 的 `notified` 超 10 分钟未 ack 自动升级到短信——「没人处理」本身会报警 | `internal/ota/service.go` `Resume`，`internal/alarm/service.go` `EscalateOnce` |

## 4. 一句话版本

> 缓存和限流是在给错误的 SQL 续命；先 `EXPLAIN`，再加索引，最后才谈限流——而限流的维度必须是「真正在发请求的那个实体」。
