教育与 B 端 AIoT 产品需求文档

xTool 设备云 BL5 业务线的产品需求：让学校与工作室以「组织」而不是「个人」管理一批机器。教室多机看板、上课时段外禁用、批量 OTA、按班级任务队列、工作室多机调度与耗材集采六个功能域，全部复用 BL1 建成的接入、影子、事件、指令、OTA 五条链路与 BL4 的 App / XCS 入口、参数库、云端下发任务，只新增组织租户模型、策略下发与任务队列三块。BL5 整体处于平台 P2 阶段，本文内部再分 P0 试点、P1 扩展、P2 商业化三档。与《xTool AIoT 平台技术方案》§1 / §6 / §12、BL4 技术方案 §4 / §6.4 / §10 及工程仓库 x-aiot 一一对应。

  • P0 必须 首批 3 到 5 所试点学校上线前必须交付
  • P1 应该 试点后首个迭代，覆盖工作室与集采
  • P2 可以 B 端订阅商业化，需 BL4 entitlement 与支付就位

01背景与目标

1.1 问题

  • 一间创客教室通常有 6 到 20 台激光机，老师上课时要同时盯所有机器的状态与安全，下课后要确保没人偷开机器。今天这些全靠人走动巡视和钥匙锁门。
  • 学校采购后固件版本很快碎片化，老师不会也不敢逐台升级；同一节课不同机器参数表现不一致，教学无法标准化。
  • 学生提交加工任务靠 U 盘和排队喊号，机器空转与拥堵并存；老师没有审批环节，学生可能切不允许的材料。
  • 工作室主每天要在十几台机器间分派任务、盯耗材，激光模块什么时候该换只能靠经验；集中采购耗材没有数据依据。
  • 设备云现有模型以「个人绑定」为中心，一台机器属于一个用户。学校的机器属于学校，老师会换、学生每年换一批，个人绑定模型无法表达。

1.2 目标

  1. 组织：设备归属组织而不是个人；组织内按教室或车间分组，成员按角色授权；老师离职、学生毕业不影响设备归属。
  2. 可见：一张看板看全组织所有机器的在线、作业、告警、待升级状态，告警仍推送到具体责任人而不是只在看板上闪。
  3. 可控：上课时段外机器自动禁用，断网也生效；解锁需要老师授权；禁用绝不影响安全功能与急停。
  4. 高效：任务按班级排队、老师审批、机器空闲即下发；批量 OTA 只在维护窗口执行且不绕过任何灰度与熔断护栏。
  5. 数据：组织级耗材健康度汇总生成集采清单，替代经验判断。

02用户、场景与用户故事

2.1 目标用户

  • 学校信息化管理员 / 采购负责人：管几十台设备的归属、账号与固件，一年操作几次但每次都是批量。
  • 创客课老师：每周上课，需要一眼看清教室里所有机器的状态，审批学生任务，下课后确认机器已锁。
  • 学生：只需提交任务、看排队进度与结果，不需要也不应该有任何控制权。
  • 工作室主 / 生产主管：一天十几个订单分派到多台机器，关心谁在忙、谁快坏、耗材什么时候补。

2.2 核心用户故事

US-1 一张看板 作为老师，我希望上课时在讲台平板上看到教室里 12 台机器谁在线、谁在切、谁报警、谁该升级，而不用走到每台机器前面看屏幕。
US-2 下课自动锁 作为老师，我希望下课铃响后机器自动进入禁用状态，学生按开始也不会出光；断网了也一样锁着；我需要临时用时能在手机上解锁。
US-3 锁不住安全 作为管理员，我希望禁用只是禁止开始新任务，火焰检测、急停、告警推送在任何状态下都正常工作，我不想为了管理牺牲安全。
US-4 排队与审批 作为学生，我希望在 XCS 里提交任务后看到自己排第几、预计几点轮到；作为老师，我希望能先看一眼学生的材料和参数再批准，不合适就退回。
US-5 统一升级 作为管理员，我希望勾选一批机器在周末凌晨统一升级固件，升级过程遵守灰度与熔断，出问题自动停下并通知我。
US-6 集采有据 作为工作室主，我希望看到每台机器激光模块与滤芯的剩余寿命汇总，导出一张下季度采购清单，而不是等哪台切不透了才买。
US-7 人走设备留 作为管理员，我希望老师离职、学生毕业时只需从组织移除成员，设备归属与历史记录不受影响。

03范围：P0 做什么、不做什么

P0 范围内（试点学校） 明确不做（留给 P1 / P2）
组织与教室两级结构，org_admin / teacher / student 三个角色 跨组织共享设备、集团多校区层级（P1）
设备归属组织；个人绑定与组织归属冲突以组织为准并留痕 设备在组织间转移的审批流（P1）
教室看板：≤ 200 台聚合状态，30 s 轮询 SSE 实时推送（P1）；自定义看板布局（P2）
时段策略：周课表 + 云端 lock desired + 设备本地时间表兜底；教师解锁 节假日日历同步、临时调课自动适配（P1）
批量 OTA：按组织圈选 + 维护窗口，复用 ota-svc 灰度熔断 组织自定义灰度比例（不提供，平台统一）
班级任务队列：提交、审批、排队、空闲下发，复用 BL4 job_start 多机自动负载均衡调度（P1，工作室场景）
告警推送到教室责任老师 + 看板聚合 告警按班级值日轮转（P2）
组织级耗材健康度只读汇总 集采清单导出与供应商对接（P1）；支付（不做）
试点 3 到 5 所学校，US 单区 B 端订阅与计费（P2，走 BL4 entitlement）

6.1 物模型 v1.2 扩展（在 BL4 v1.1 之上）

6.3 数据归属与保留

  • 组织数据（org / site / member）长期保留；成员 removed_at 软删。
  • lock_audit 与 queue_item 保留 2 年，按月分区。
  • 设备解除组织归属后，该设备在组织内的 job_record 与 queue_item 留在组织（属于组织的教学记录），设备本身的遥测按 BL1 规则归 SN。
  • 学生为未成年人的可能性高：student 角色只存 user_id，不采集任何额外个人信息；提交的文件走 BL4 预签名 URL 1 h 不持久化。

10依赖、风险与开放问题

10.1 依赖

  • BL1 平台：deviceapi desired 新字段 lock / lock_expires_at / schedule；ota-svc 批次增加 policy.window；alarm-svc 不改，订阅关系在 fleet-svc。
  • BL4：BFF 鉴权框架扩展 org 维度；云端下发任务 job_start（FR-414）必须先通过安全评审，队列调度依赖它；entitlement（P2）。
  • BL3：consumable_health 数据用于集采汇总。
  • 固件：DR-501 到 DR-504，其中 locked 不影响安全与本地课表兜底是红线。
  • 法务与学校：学生数据最小化、试点协议、未成年人相关合规意见。
  • App / XCS 团队：组织入口、讲台看板模式、队列提交与审批界面。

10.2 风险与对策

风险 影响 对策
禁用逻辑误伤安全功能 安全事故，且发生在学校 DR-501 红线台架测试；禁用只作用于「开始新任务」一个动作；安全链路与 fleet-svc 零依赖
本地时钟漂移导致上课时锁死 教学中断 RTC 漂移 > 10 min 以云端最后指令为准；教师解锁始终可用；屏幕解锁码（P1）
租户越权看到其他学校 隐私与合规 所有查询带 org_id；BFF 路由组级中间件；越权测试进 CI
队列调度器重复下发同一任务 材料报废 queue_item 状态机条件 UPDATE；设备端单任务约束；job_start 幂等
批量 OTA 校园带宽打满 网络瓶颈影响教学 站点并发 ≤ 5；只在维护窗口
个人绑定与组织归属冲突处理不清 用户困惑与投诉 组织优先 + 留痕 + 通知；个人 App 明确显示「由组织管理」
学生数据合规 法律风险 只存 user_id；文件不持久化；试点前法务意见

10.3 开放问题

  1. 学生角色是否允许局域网直连绕过队列直接加工？建议由组织策略决定，默认试点学校关闭。
  2. 组织归属后个人绑定用户是否保留告警推送？建议保留（多一个人知道机器停了不是坏事），但不保留控制权。
  3. 教师解锁上限 240 分钟是否合理，是否允许 org_admin 设置更长的「活动日」解锁。
  4. 队列调度是否需要考虑材料库存（同一种材料多少张）。
  5. 集团多校区的付费是按组织还是按父组织计。
